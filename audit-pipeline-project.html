Audit-ready data pipeline

An end-to-end pipeline for NHS-style outpatient data where every step can be proven to an auditor: what data came in, which rules it was checked against, what was removed or pseudonymised, which model scored it, and that none of the records were changed afterwards.

All data in this project is synthetic, generated with a fixed random seed. No real patient information is used. It demonstrates audit and privacy controls; it is not a certified compliance product.

The problem

Regulated organisations such as NHS trusts, insurers and banks are increasingly asked: “Can you show exactly how this number, or this prediction, was produced?” Most pipelines can’t answer that:

  • Bad records are silently dropped or “fixed”, so totals can’t be reconciled
  • Patient identifiers flow further into reporting than they need to
  • Logs can be edited after the fact, so they prove nothing
  • Models are trained and deployed with no record of the data, version or fairness checks behind them

The use case: predict which outpatient appointments are likely to be missed (“Did Not Attend”), so staff can make an extra reminder call to the highest-risk 20%.

What I built

  1. A tamper-evident audit log. Every action is written as a JSON line that includes the SHA-256 hash of the previous line. Editing, deleting or reordering any entry breaks the chain, and the pipeline refuses to run if the log has been altered.
  2. Data contracts with quarantine. 37 versioned rules in YAML, including the NHS number modulus-11 check digit, valid codes, impossible dates, duplicates and foreign keys. Failing rows are kept unchanged with the exact rules they broke, never silently fixed.
  3. Privacy by design. NHS numbers replaced with a keyed HMAC-SHA256 pseudonym, names and phone numbers dropped, date of birth reduced to age bands and postcode to district. An automated PII scan stops the run if anything identifiable is left.
  4. A traceable star schema. Every warehouse row carries the run ID, source file hash and load time, with foreign keys enforced. SQL is written to port to Snowflake.
  5. Lineage and fingerprints. Every dataset is hashed at every stage, and source-to-target lineage is recorded and drawn as a diagram.
  6. A governed ML model. Time-based split with no future leakage, two models compared on a rule set before training, sex excluded as a feature, model file hashed, and a model card generated automatically.
  7. Fairness testing. For every sex, age band and deprivation decile, predicted risk must be within 3 points of the actual missed-appointment rate. Failures are logged as warnings.
  8. An HTML audit report. One page per run with lineage, rule results, privacy actions, model card, fairness table and the verified audit trail.

Results

The selected model (logistic regression, ROC AUC 0.685 on a time-based hold-out) flags the top 20% of appointments and catches 39% of missed appointments at 35% precision, about 1.9× better than calling patients at random.

Key findings

  • Changing a single number in the audit log is caught immediately: “TAMPERING DETECTED: content changed after it was written”.
  • Appointments with no reminder are missed 24% of the time, against 16% with one, the clearest lever for reducing missed appointments.
  • Patients in the most deprived areas (deciles 1–2) miss about 23% of appointments against 14% in the least deprived.
  • The fairness check flagged one group for review: deprivation decile 4, where the model overstates risk by 4 points. The cause is that it treats deprivation as a straight line while the real effect is a step; the fix is to model it as categories.

What I’d improve next

  • Run on real public data (NHS Digital outpatient activity) and on Snowflake
  • Replace the SQL scripts with dbt models and tests
  • Schedule it with Airflow, with alerts when a contract or fairness check fails
  • Add a Power BI dashboard on the reporting views and audit tables
  • Store the audit log in append-only cloud storage
